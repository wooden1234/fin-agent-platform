# 财务语义层与口径解析设计

## 1. 背景与目标

当前 predefined 白名单查询链路在三个场景下存在结构性问题：

1. **同义指标跨公司不统一**：用户说「营业收入」，腾讯年报字段是「收入」，宁德时代是「营业收入(千元)」，旧链路用全局 `metric_id IN (...)` 无法正确映射。
2. **年度口径与季度口径冲突**：`annual_financial_facts` 同时存 annual / quarter，旧 SQL 默认只查 annual，当年报缺少年值但四季度齐全时无法兜底。
3. **compare 假设单一 metric_id**：`company_id IN (...) AND metric_id IN (...)` 隐含所有公司共用同一指标主键，跨公司对比会查错或查空。

本方案在 **predefined 执行前** 增加语义层，职责单一、边界清晰，不负责 planner 路由、SQL 生成大模型、最终回答大模型。

## 2. 架构与工作流

```mermaid
flowchart LR
    planner[planner] --> toolSelection[tool_selection]
    toolSelection --> registry[canonical_metric_registry]
    registry --> coverage[coverage_resolver]
    coverage --> sqlBuilder[sql_builder]
    sqlBuilder --> execute[execute]
    execute --> formatter[answer_formatter]
```

### 模块职责

| 模块 | 职责 | 不负责 |
|------|------|--------|
| `tool_selection` | 选模板、抽原始槽位 | 指标语义、口径决策 |
| `canonical_metric_registry` | 用户指标词 → canonical code → 公司级 source metric | SQL、答案文案 |
| `coverage_resolver` | 判断公司/年份/粒度是否可查，选策略 | 路由、SQL 生成 |
| `sql_builder` | 按 binding 生成 OR 子句 SQL | 语义映射 |
| `execute` | 执行 SQL、四季度后聚合 | 文案 |
| `formatter` | 答案 + 口径说明 | 查询逻辑 |

## 3. 数据模型

### 3.1 语义层核心类型

- `CanonicalMetricDefinition`：统一指标码（如 `REVENUE`）
- `CompanyMetricOverride`：公司级字段名覆盖（只存 `metric_name`，不存 `metric_id`）
- `CanonicalMetricMatch`：一次用户指标词的标准化结果
- `CompanyMetricMatch`：某公司下的 source metric 映射
- `CoverageRequest` / `CoverageResolution`：口径探测输入输出
- `CompanyCoverage`：单公司可用年份、粒度、选定策略
- `ResolvedMetricBinding`：SQL 执行用的 `(company_id, metric_id, strategy)` 绑定

### 3.2 策略枚举

| 策略 | 含义 |
|------|------|
| `annual_direct` | 直接取 `period_type=annual` |
| `sum_quarters` | 查四季度明细，Python 层汇总 |
| `latest_annual` | 取最近年度 |
| `latest_available` | 取最近可用记录 |
| `partial_compare` | 对比时部分公司有数据 |
| `clarify_for_granularity` | 需用户确认粒度 |
| `unavailable` | 不可查 |

### 3.3 场景规则（第一版）

| 查询类型 | 策略优先级 |
|----------|------------|
| `latest` | `annual_direct` → `latest_available` |
| `lookup` | `annual_direct` → 四季度齐全则 `sum_quarters` |
| `compare` | 双方 `annual_direct`；否则允许混合口径并声明 |
| `trend` | 按年逐条判断，缺年跳过并标注 |

## 4. 现有数据表设计（fin_core）

语义层第一版**不新增数据库表**，直接查询现有五表：

### 4.1 `financial_companies`

公司维度：`id`, `company_key`, `name`, `ticker`。

### 4.2 `annual_report_documents`

年报文档：`company_id`, `fiscal_year`, `doc_id`, `source`。

### 4.3 `annual_financial_tables`

文档内表格分块，事实通过 `table_id` 关联。

### 4.4 `financial_metrics`

指标字典：`id`（即 fact 中的 `metric_id`）、`canonical_name`、`aliases`。

> 注意：`canonical_name` 是报告原生名称，**不是**全局统一语义码；跨公司统一语义由代码内 `registry_seed.py` 维护。

### 4.5 `annual_financial_facts`

窄表事实，关键字段：

| 字段 | 说明 |
|------|------|
| `metric_id` | 关联 `financial_metrics.id` |
| `period_label` | 原始期间标签，如 `2024年`、`第一季度` |
| `period_year` | 规范化年份 |
| `period_type` | `annual` / `quarter` / `period_end` / `change_rate` / `unknown` |
| `value` / `raw_value` | 数值 |

年度与季度共存于同一张表，由 `period_type` 区分。

## 5. 语义注册表设计

### 5.1 第一版：代码内 seed（`registry_seed.py`）

三层结构：

1. **canonical metrics**：`REVENUE`, `NET_INCOME_ATTR_PARENT`, `OPERATING_PROFIT`, `RND_EXPENSE`, `OPERATING_CASHFLOW_NET`
2. **global aliases**：`"营业收入" -> REVENUE`, `"净利润" -> NET_INCOME_ATTR_PARENT` 等
3. **company overrides**（只存名称）：

| company_key | canonical | DB metric_name |
|-------------|-----------|----------------|
| Tencent | REVENUE | 收入 |
| Tencent | NET_INCOME_ATTR_PARENT | 本公司權益持有人應佔盈利 |
| CATL | REVENUE | 营业收入(千元) / 营业收入 |
| CATL | NET_INCOME_ATTR_PARENT | 归属于上市公司股东的净利润 |

`metric_id` 在运行时按 **公司 + metric_name** 查库解析，避免导入批次导致 ID 漂移。

### 5.2 未来迁表设计（v2，当前不实现）

```sql
CREATE TABLE fin_core.canonical_metrics (
  code VARCHAR(64) PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  description TEXT
);

CREATE TABLE fin_core.canonical_metric_aliases (
  alias VARCHAR(255) NOT NULL,
  canonical_code VARCHAR(64) REFERENCES canonical_metrics(code),
  UNIQUE(alias, canonical_code)
);

CREATE TABLE fin_core.company_metric_overrides (
  company_id INT REFERENCES financial_companies(id),
  canonical_code VARCHAR(64) REFERENCES canonical_metrics(code),
  metric_name VARCHAR(255) NOT NULL,
  PRIMARY KEY (company_id, canonical_code)
);
```

## 6. SQL Binding 设计

### 6.1 旧模式（已废弃用于多公司 compare）

```sql
WHERE document.company_id IN (:company_ids)
  AND fact.metric_id IN (:metric_ids)
```

问题：笛卡尔积 + 假设所有公司共用 metric_id。

### 6.2 新模式：公司级 binding

```sql
WHERE (
  (document.company_id = :company_id_0 AND fact.metric_id = :metric_id_0)
  OR (document.company_id = :company_id_1 AND fact.metric_id = :metric_id_1)
)
```

每个 binding 还可附带不同 `period_type` 过滤（annual vs quarter）。

## 7. sum_quarters 后处理

1. `coverage_resolver` 判定目标年四季度齐全 → 策略 `sum_quarters`
2. SQL 查询 `period_type = 'quarter'` 的四条明细
3. `quarter_aggregate.py` 按 `(company_id, metric_id, year)` 求和
4. 生成 `period_label = '四季度汇总'` 的合成年度行
5. `formatter` 在答案中声明口径

## 8. 答案口径说明

`formatter` 根据 `CoverageResolution.answer_policy` 追加说明，例如：

- 腾讯按「收入」字段映射为营业收入语义
- 宁德时代 2024 年值由四季度汇总
- 对比结果包含不同口径来源，请在解读时注意字段差异

## 9. 接入点与迁移

- **入口**：[`predefined/node.py`](../app/agents/components/finance_agent/financial_query_agent/predefined/node.py) 编排完整节点链
- **组装**：[`predefined/resolver.py`](../app/agents/components/finance_agent/financial_query_agent/predefined/resolver.py) 将语义结果转为 `ResolvedPredefinedQuery`
- **兼容**：`ResolvedPredefinedQuery.metric_ids` 保留为 computed property
- **收敛**：`EntityResolver` 中 metric 别名逐步迁入 `registry_seed.py`；`predefined/extraction/` 为遗留路径，主流程不经过
