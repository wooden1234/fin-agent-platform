# 企业级财务事实查询与模板路由方案

## 背景

当前财务事实查询链路大致如下：

```text
用户问题
  -> LLM 抽取固定参数
  -> 模板匹配
  -> 命中模板则执行结构化查询
  -> 未命中则走 text-to-SQL
```

这条链路适合快速验证能力，但随着问题类型增加，会逐步暴露两个核心问题：

- 参数抽取协议过于硬编码，`companies / years / metrics / operation` 只能覆盖有限问题。
- 查询主链路依赖 `ilike` 和模糊匹配，准确率、性能、可解释性都容易成为瓶颈。

本文档聚焦这两个问题，整理适合企业项目的演进方案。

## 当前主要问题

### 1. 参数抽取过于固定

当前 `FinancialFactQuery` 更像是为少数高频问题定制的 DTO：

```python
companies: list[str]
years: list[int]
metrics: list[str]
operation: Literal["lookup", "latest", "compare", "trend"]
top_k: int
```

这个结构可以支撑：

- 单公司单年份单指标查数
- 最新一期指标查询
- 简单对比
- 简单趋势

但一旦问题扩展，就会明显吃力。例如：

- 排名类：`2024 年营收最高的前 10 家公司`
- 过滤类：`资产负债率超过 70% 的公司`
- 计算类：`2022 到 2024 年营收 CAGR`
- 条件类：`净利润同比下滑的公司`
- 口径类：`归母净利润`、`扣非净利润`、`经营性现金流`

如果继续往一个类里不断加字段，下游所有模板、SQL 构造、日志、测试都会跟着膨胀。

### 2. `ilike` 不适合做主查询策略

当前做法更接近：

```text
原始字符串
  -> 别名映射
  -> ilike("%term%")
  -> 命中事实表
```

这个方案在早期很省事，但企业场景里有几个明显风险：

- 指标歧义大：`利润` 可能命中 `净利润`、`归母净利润`、`营业利润`。
- 公司表达多样：简称、英文名、股票代码、历史名称混杂。
- 性能不稳定：`%term%` 难以稳定利用普通索引。
- 结果不可解释：只知道“查到了”，很难解释“为什么是这个结果”。
- 主查询条件过于模糊时，结构化库容易返回看似相关但口径错误的数据。

因此，`ilike` 可以保留，但不应继续作为财务事实查询的主路径。

## 企业级设计原则

企业里更常见的思路不是让 LLM 直接决定最终查询，而是把它放在“理解用户表达”的位置，后续由可控系统接管：

```text
用户问题
  -> Query Understanding
  -> Entity Resolver
  -> Template Matcher
  -> Query Planner
  -> Executor
  -> Answer Formatter
```

核心原则如下：

- LLM 负责理解，不直接决定最终 SQL。
- 模板负责高频、高价值、高准确率场景。
- text-to-SQL 负责长尾和探索型问题。
- 实体标准化优先于模糊查询。
- 财务数值查询优先走 ID、字典和规则，不直接依赖字符串模糊匹配。

## 推荐分层模型

### 第一层：LLM 原始抽取层

这一层只表达“用户想问什么”，不直接作为所有下游协议。

示例：

```python
class FinancialFactExtraction(BaseModel):
    intent: str = "lookup"
    companies: list[str] = Field(default_factory=list)
    metrics: list[str] = Field(default_factory=list)
    years: list[int] = Field(default_factory=list)
    filters: list[dict] = Field(default_factory=list)
    dimensions: list[str] = Field(default_factory=list)
    order_by: list[dict] = Field(default_factory=list)
    calculations: list[dict] = Field(default_factory=list)
    top_k: int | None = None
    extra: dict = Field(default_factory=dict)
```

这一层允许宽松、不完整，也允许保留歧义。

### 第二层：标准化意图层

这一层负责把自然语言转成系统内部可执行的标准对象。

示例：

```python
class FinancialQueryIntent(BaseModel):
    company_ids: list[int] = Field(default_factory=list)
    metric_ids: list[int] = Field(default_factory=list)
    years: list[int] = Field(default_factory=list)
    intent: str = "lookup"
    filters: list[dict] = Field(default_factory=list)
    ambiguity: list[dict] = Field(default_factory=list)
    limit: int = 5
```

进入这一层之后，下游尽量使用 `company_id`、`metric_id`、`period_year` 这类稳定字段，而不是继续处理原始字符串。

### 第三层：模板执行计划层

模板层不直接消费原始问题，而是消费标准化后的意图，并生成真正的查询计划。

示例：

```python
class FinancialQueryPlan(BaseModel):
    route: str
    template_id: str | None = None
    template_version: str | None = None
    slots: dict = Field(default_factory=dict)
    filters: list[dict] = Field(default_factory=list)
    result_shape: str = "facts"
```

## Entity Resolver 设计

`EntityResolver` 是整个模块最关键的中间层，职责是把用户表达映射到稳定实体。

建议拆成三个子能力：

- `resolve_company`
- `resolve_metric`
- `resolve_time`

### 公司解析建议

优先级建议如下：

```text
股票代码精确匹配
  -> 公司全称精确匹配
  -> 公司别名 / 英文名 / 简称词典匹配
  -> 规范化匹配
  -> trigram / full-text / embedding 召回
  -> 候选歧义
```

最终返回结果建议包含置信度和原因：

```python
{
    "entity_type": "company",
    "input": "宁德",
    "candidates": [
        {"id": 101, "name": "宁德时代", "confidence": 0.95, "reason": "alias_exact"}
    ]
}
```

### 指标解析建议

指标解析建议显式维护指标字典，而不是只依赖 `FinancialMetric.canonical_name` 的模糊包含。

指标字典至少应包含：

- 指标标准名
- 常见中文别名
- 英文名称
- 报表类型
- 单位和币种
- 口径说明
- 可支持模板

例如：

```text
营收 -> 营业收入
净利 -> 归属于母公司股东的净利润
归母净利 -> 归属于母公司股东的净利润
经营现金流 -> 经营活动产生的现金流量净额
```

如果用户只问“利润”，建议不要直接下结论，而是：

- 返回多个候选指标
- 降低置信度
- 进入澄清或 fallback

### 时间解析建议

时间不应只保留 `years`，建议解析更完整的时间语义，例如：

- 单年：`2024`
- 多年：`2022-2024`
- 最新：`latest`
- 历年：`all_available_years`
- 当前财年：需要结合业务定义

## Template Matcher 设计

模板匹配不建议依赖单一魔法分数或统一阈值，而应采用：

```text
硬规则门控
  -> 候选模板打分排序
  -> 风险分层决策
```

### 1. 先做硬规则门控

例如：

`exact_metric_lookup`

- 必须有唯一公司
- 必须有唯一指标
- 必须有唯一年份
- 不能包含排名、聚合、筛选语义

`latest_metric_lookup`

- 必须有唯一公司
- 必须有唯一指标
- 没有明确年份
- 有 `latest/current/recent` 语义，或上游 intent 已识别为 `latest`

`trend_metric_lookup`

- 必须有公司和指标
- 必须有多年份，或问题中有 `趋势/历年/近几年`

没通过硬规则的模板，直接不参与后续竞争。

### 2. 再做可解释打分

分数只在多个模板都“有资格执行”时使用，用来排序，而不是决定一切。

建议每个模板输出：

```python
class TemplateMatchResult(BaseModel):
    template_id: str
    score: float
    passed: bool
    reasons: list[str] = Field(default_factory=list)
    missing_slots: list[str] = Field(default_factory=list)
```

例如：

```text
template=trend_metric_lookup
score=0.91
reasons:
- intent=trend
- company resolved exactly
- metric alias resolved
- multi-year detected
```

### 3. 风险分层决策

不要简单做：

```python
if score > threshold:
    run_template()
else:
    text_to_sql()
```

更稳的做法是：

```text
高置信：
  直接走模板

中置信：
  视情况澄清、返回候选、或走受限模板

低置信：
  走 text-to-SQL / RAG / 拒答
```

此外，建议同时考虑：

- 模板自己的阈值
- `top1 - top2` 的分差
- 关键实体是否唯一
- 是否存在明显歧义

金融场景里，宁可保守一点，也不要自信答错。

## `ilike` 和模糊检索的推荐位置

建议把 `ilike` 从“事实查询主条件”降级为“实体召回手段”。

推荐链路：

```text
用户问题
  -> Resolver 阶段：
     alias / exact / normalization / trigram / ilike 召回候选
  -> 产出标准实体 ID
  -> Fact 查询阶段：
     company_id / metric_id / year 精确过滤
```

也就是说：

- `ilike` 可以存在，但放在 resolver 中使用。
- 事实表查询阶段尽量不要用 `%term%` 作为核心条件。
- 主查询最好围绕 `company_id`、`metric_id`、`period_year` 展开。

如果后端数据库是 PostgreSQL，后续可以考虑：

- `pg_trgm` 做相似度召回
- 全文检索处理较长别名
- 结果带相似度分数，供 resolver 判断置信度

## 推荐整体流程

综合以上建议，推荐链路如下：

```text
用户问题
  -> LLM 抽取宽松语义帧
  -> EntityResolver 标准化公司 / 指标 / 时间
  -> TemplateMatcher 进行硬规则门控和候选排序
  -> 高置信命中模板：
       走模板 executor
  -> 低置信或长尾问题：
       走 text-to-SQL
  -> 输出结构化结果和来源信息
```

可进一步细化为：

```text
QueryUnderstanding
  -> ResolvedIntent
  -> TemplateQueryPlan / TextToSQLPlan
  -> Executor
  -> Formatter
```

## 对当前项目的落地建议

建议按低风险方式逐步演进，而不是一次性大重构。

### 第一阶段

- 将 `FinancialFactQuery` 降级为 LLM 抽取 DTO。
- 新增 `EntityResolver` 层，先只处理公司、指标、年份。
- 模板只消费标准化后的实体，不再直接吃原始字符串。

### 第二阶段

- 把公司别名和指标别名从 service 中抽离，沉到字典或维表。
- 将 `latest / compare / trend` 查询逻辑改成基于 ID 的执行路径。
- 让 `ilike` 只保留在 resolver 召回阶段。

### 第三阶段

- 引入更完整的模板注册器。
- 为模板匹配增加 `reasons / missing_slots / confidence`。
- 根据离线评估结果调整模板 gate 和风险分层策略。

## 不建议继续扩大的方向

以下方向短期看起来省事，但长期维护成本会很高：

- 持续向 `FinancialFactQuery` 增加更多固定字段。
- 在事实查询主 SQL 中继续堆叠更多 `ilike("%term%")`。
- 用一个统一阈值控制所有模板。
- 让模板直接消费 LLM 原始字符串，不经过标准化。
- 把所有长尾问题都强行塞进模板系统。

## 结论

企业级财务事实查询模块的关键，不是把 prompt 写得更复杂，也不是把 `ilike` 调得更宽，而是把链路拆清楚：

```text
LLM 负责理解
Resolver 负责标准化
Template 负责高频准确场景
Text-to-SQL 负责长尾问题
结构化查询尽量基于稳定 ID
模糊查询只作为召回和兜底手段
```

如果后续继续演进，建议优先建设：

- 公司和指标语义字典
- 实体标准化层
- 模板注册与执行框架
- 模板命中评估和歧义回放机制

这几项打稳后，模板系统和 text-to-SQL 才会真正形成互补关系，而不是互相打架。
